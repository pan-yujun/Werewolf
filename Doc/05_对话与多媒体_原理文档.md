# 模块 05 - 对话、语音与多媒体交互 - 原理文档

Wolfcha 之所以能给玩家带来极强的桌游沉浸感，不仅依靠优秀的 AI 推理心智，还得益于精细的前端交互细节：包括气泡文本的流式打字渲染、异步语音的合成缓存以及高同步的队列音视频控制。

---

## 一、 流式发言段落切分原理 (`StreamingSpeechParser`)

在白天发言阶段，如果让玩家等待大模型吐完几百字的发言，再让 UI 显示气泡并合成语音，会有长达 8-15 秒的死寂等待，极大地损坏了游戏的互动心智。

为了实现零等待的流畅交互，系统通过 **StreamingSpeechParser** 配合大模型的流式 SSE 协议完成了“边吐字、边提取、边播报”的管道机制：

```
大模型流式 SSE 输出: "我觉得3号是个铁狼。理由有两点：第一..."
                             │
                             ▼ (逐字喂给 StreamingSpeechParser)
       [检测到中英文句号/感叹号/换行符 (。/！/\n) 等边界]
                             │
                             ▼
         [剥离、拼装出第一个完整句段 Segment 0]
                             │
            ┌────────────────┴────────────────┐
            ▼                                 ▼
   [UI 打字机立刻渲染 Segment 0]     [调度 TTS 接口合成 Segment 0 并播放]
```

### 1.1 段落切分的边界条件
切分器维护一个累加缓冲区。当检测到以下字符时判定为当前的语义段落结束：
*   特定断句符号：中文的句号（`。`）、问号（`？`）、叹号（`！`）、省略号，或英文的 `.`、`?`、`!`。
*   JSON 数组围栏：如果是以 JSON 格式输出的数组段，切分器会自动解析其中的字符串项。

### 1.2 预取机制 (Speech Prefetching)
为了让下一位 AI 玩家的发言衔接得天衣无缝，在**当前发言玩家还在说最后一句话时**，系统便已在后台悄悄调起了下一位 AI 玩家的 `generateAISpeechSegmentsStream`。在下一位玩家轮次启动时，第一句话（Segment 0）可能已经预取并合成完毕，达成秒开播放。

## 二、 音频串行调度与同步原理 (`AudioManager`)

所有的 TTS 合成语音与主持法官旁白如果并发播放，会导致声音相互踩踏、人声嘈杂。系统在底层实现了一个轻量级的**串行音频调度队列**。

### 2.1 任务化音频队列 (Task Queue)
`AudioManager` 将每一段配音抽象为一个 `AudioTask`，其核心属性包括：
*   `id`：唯一任务标识，通常以 `voiceId_hash` 组成，防止同一段话被重复下载与播放。
*   `text`：被播报的物理文本。
*   `audio`：指向浏览器 `HTMLAudioElement` 的实体。

### 2.2 串行流动机制
1.  **非阻塞入队**：TTS 接口返回的音频 URL 被实例化为任务推入内部队列 `queue`。
2.  **串行播放**：AudioManager 检测当前是否有正在播放的音轨。若无，则取出队首任务执行播放。
3.  **事件监听机制**：通过为 HTMLAudioElement 挂载 `onplay`、`onpause` 和 `onended` 事件，AudioManager 实现了高精度的生命周期管理。当 `onended` 触发，调用 `playNext()`，将下一个 AI 气泡或系统指令顺序输出，实现连贯流畅的“舞台对话感”。

## 三、 UI打字机步调协同 (`useTypewriter`)

网页端的气泡文字以“逐字蹦出”的形式表现。为了防止文字打字速度与 TTS 播放人声语速发生明显的偏差，打字机速度并不是一成不变的常量：
*   打字机组件会监听 `useTypewriter` 的步调触发器。
*   其核心算法会根据当前待打字句子的长度，并结合 TTS 音频的总长度，动态算出一个合理的时间差，使文本排版与声波振幅达到视觉与听觉的高度重合。
